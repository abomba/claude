# qcdb

PostgreSQL database, loader and (from stage 3/4) web dashboard for per-sample bacterial WGS QC
results produced by the lab's Nextflow pipeline. The design is in
[`docs/design/01-design.md`](docs/design/01-design.md).

Status: **stage 4 (dashboard)**. Deployment (Docker Compose) follows in stage 5.

**Demo:** a read-only demo with fictional fixture data is published to GitHub Pages by
`.github/workflows/pages.yml` (see [Demo on GitHub Pages](#demo-on-github-pages)).

## Layout

| Path | Content |
|---|---|
| `frontend/` | React + TypeScript dashboard (Polish UI), Playwright e2e tests |
| `backend/` | Python package `qcdb`: models, Alembic migration, loader CLI, tests |
| `backend/src/qcdb/data/` | versioned metric dictionary and JSON Schemas |
| `fixtures/` | fictional result directories generated by `backend/tests/fixtures/build.py` |
| `modules/local/qcdb_load/main.nf` | Nextflow module `QCDB_LOAD` |
| `spec/` | verbatim copies of the reference material from the brief |
| `docs/` | design, validation checklist |

## Loader quick start (development)

```bash
cd backend
python3 -m venv .venv && .venv/bin/pip install -e ".[dev]"
export QCDB_DATABASE_URL=postgresql://qcdb@localhost:5432/qcdb   # password: PGPASSWORD or QCDB_DATABASE_PASSWORD_FILE
.venv/bin/alembic -c alembic.ini upgrade head
.venv/bin/qcdb import-dictionary src/qcdb/data/metric_dictionary.psv
.venv/bin/qcdb load ../fixtures/RUN_2606 --dry-run
.venv/bin/qcdb load ../fixtures/RUN_2606 --run-date 2026-06-30
.venv/bin/qcdb load ../fixtures/orders
```

```text
qcdb load <directory> [--run-id ID] [--run-date YYYY-MM-DD] [--metadata FILE] [--dry-run]
qcdb import-dictionary <file> [--labels LANG]
```

Exit codes: `0` success, `1` validation failure (any rejected document or sample), `2` usage
error (nothing loaded), `3` unreadable input (only when nothing was rejected). Credentials come
only from `QCDB_DATABASE_URL` / `PG*` variables and `QCDB_DATABASE_PASSWORD_FILE`; passwords are
never printed.

`--metadata` takes a CSV/TSV with `sample_id` and optional `run_id`, `run_date`, `order_id` and
one column per configured sample field (`material_type`, `collection_site`, `collection_date`,
`expected_species` initially). Empty cells change nothing.

## API (development)

```bash
cd backend
.venv/bin/qcdb create-user admin --role admin        # password from the terminal or stdin
QCDB_COOKIE_SECURE=false .venv/bin/uvicorn --factory qcdb.api.app:create_app --no-access-log
```

* OpenAPI: `GET /api/v1/openapi.json`, committed as `backend/openapi.json`
  (`python -m qcdb.api.openapi > openapi.json`; a test fails when it is stale). Swagger UI is
  disabled because it loads assets from a CDN.
* Login: `POST /api/v1/auth/login` sets an HttpOnly, Secure, SameSite=Strict session cookie and
  returns a CSRF token; send it as `X-CSRF-Token` on POST/PUT/PATCH/DELETE.
* `QCDB_COOKIE_SECURE=false` only for local HTTP development. Other settings:
  `QCDB_SESSION_IDLE_MINUTES` (480), `QCDB_LOGIN_MAX_FAILURES` (5), `QCDB_LOGIN_LOCK_MINUTES` (15).
* Roles: `viewer` reads results without owner e-mail, raw `data`/`inputs`, file names, `meta` and
  server paths (tool messages have paths shortened to file names); `bioinformatician` also edits
  owners, orders, samples, run dates and current versions; `admin` also manages users, sample
  fields, erasure and the audit log.
* Access logs contain method, path, status and duration only (no query strings, no bodies).

## Dashboard (development)

```bash
cd frontend
npm ci
QCDB_API_URL=http://127.0.0.1:8000 npm run dev      # proxies /api to the API
npm run build                                       # static files in dist/
```

The UI is Polish; stored values (PASS, ok, ...) are shown with Polish descriptions. Every
asset is bundled (no CDN). Metric labels and units come from `/api/v1/metrics`, with Polish
labels from `backend/src/qcdb/data/metric_labels.pl.psv`
(`qcdb import-dictionary --labels pl <file>`); a metric without a Polish label falls back to the
English dictionary label, so new metrics need no frontend change.

### End-to-end tests

```bash
cd frontend
QCDB_E2E_SERVER=postgresql://postgres@localhost:5432 npx playwright test
```

They seed the database `qcdb_e2e` from `fixtures/` (`backend/scripts/seed_fixtures.py
--recreate`), start the real API and `vite preview`, and save screenshots to
`docs/screenshots/`.

### Demo on GitHub Pages

`.github/workflows/pages.yml` (started manually: **Actions → Demo (GitHub Pages) → Run
workflow**) runs the real API on the fixture database in the workflow,
records every GET response the dashboard makes while visiting all views
(`frontend/e2e/demo-record.spec.ts`), and publishes a build in demo mode (hash URLs, read only,
bioinformatician view, no login) that reads those recorded responses. Filters that were not
recorded show a notice. One-time setup in the repository: **Settings → Pages → Source: GitHub
Actions**; deployments from branches other than the default branch must be allowed in
**Settings → Environments → github-pages**.

## Tests

The tests need a real PostgreSQL (16 is used here):

```bash
cd backend
export QCDB_TEST_DATABASE_URL=postgresql+psycopg://postgres@localhost:5432/postgres
.venv/bin/pytest
.venv/bin/ruff check src tests && .venv/bin/ruff format --check src tests && .venv/bin/mypy
```

Without `QCDB_TEST_DATABASE_URL` the tests use testcontainers (`pip install testcontainers`,
Docker required). After changing `tests/fixtures/build.py`, regenerate the fixtures with
`python tests/fixtures/build.py`.
